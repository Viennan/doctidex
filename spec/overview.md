# doctidex 协议概览

状态：Draft
版本：`v0.1.0`

本文档定义 `doctidex` 的最小协议雏形。当前版本处于 `0.y.z` 开发阶段，其兼容性按
第 1.2 节管理。

## 1. 目标

`doctidex` 是供人类与 agent 共同创建、审阅和使用的目录树结构规范。
它采用普通目录与 Markdown 作为基础，目标是：

- 保持内容可直接阅读、编辑、比较和传输；
- 以尽可能少的格式限制，为引用、发现和工具扩展保留空间。

`doctidex` 不规定知识分类体系、存储服务、查询引擎或具体 agent 的工作流。

### 1.1 协议边界

协议正文只规定一个 `doctidex` 目录树应该具有的可观察结构、内容语义与符合性
条件，不规定如何实现、构建或维护目录树。

创建、解析、校验、生成、更新和存储等过程由不同实现变体自行决定。只要最终的
目录树符合协议，其实现方法不属于协议要求。这类似视频编码标准规定码流的形式
与语义，而不规定编码器和解码器的具体实现。

### 1.2 版本号与升级规则

doctidex 标准使用 `vMAJOR.MINOR.PATCH` 三段式版本号。`v` 是标准版本标识的一部分；
`MAJOR`、`MINOR` 和 `PATCH` 均为不带前导零的非负十进制整数，数值 `0` 除外。标准
版本不增加第四段、预发布后缀或构建后缀；Draft、稳定等发布状态与版本号分开表达。

当前标准版本为 `v0.1.0`。

达到稳定兼容阶段后，各段按以下规则升级：

| 版本段 | 升级条件 |
|---|---|
| `MAJOR` | 发生不兼容的规范变更。例如原本符合的目录树变得不符合，既有必需结构被删除或改名，或者既有可观察语义被改变。 |
| `MINOR` | 增加向后兼容的规范能力。例如增加可选结构或语义、放宽约束，并保证既有符合目录树仍然符合、既有结构的含义不变。 |
| `PATCH` | 只进行不改变符合性集合和可观察语义的修订。例如纠正文字、消除不改变要求的歧义，或修正与现有规则一致的示例。 |

`0.y.z` 表示首个稳定兼容基线之前的开发阶段。在这一阶段：

- 任何改变符合性条件、必需结构或可观察语义的规范变更，无论是否向后兼容，均至少
  升级 `MINOR`；该版本可能包含不兼容变化，发布说明必须明确标识迁移影响；
- `PATCH` 仍只允许不改变符合性和可观察语义的修订；
- `v1.0.0` 表示首个稳定兼容基线，此后完整采用上表中的 `MAJOR`、`MINOR`、`PATCH`
  规则。

一次发布包含多类变更时，按影响最大的变更升级且只升级对应的一段；升级 `MAJOR` 时
将 `MINOR`、`PATCH` 归零，升级 `MINOR` 时将 `PATCH` 归零。已发布的版本号不得复用，
其协议内容不得原地改写；任何需要改变已发布协议内容的后续发布都必须使用更高版本。

版本号描述整份 doctidex 标准，不是实现包版本、内部数据格式版本或单个目录树的内容
版本。当前协议不要求目录树在 `index.md` 中声明所遵循的标准版本；若未来引入此类
字段，必须通过相应版本的协议另行定义。

## 2. 术语

- **doctidex 目录树**：一个遵循本协议的目录树。
- **根目录**：其 `index.md` frontmatter 中 `doctidex.root` 为 `true` 的目录。
- **目录树名称**：根目录的目录名。当前仅作为本地名称，不作为全局唯一标识。
- **索引文件**：名为 `index.md` 的目录入口文档。
- **变更记录**：名为 `log.md` 的可选历史文档。
- **内部路径**：以 doctidex 根目录为基准、位于该目录树内的路径。
- **绝对内部路径**：以 `/` 开头、相对于 doctidex 根目录的内部路径，不是文件系统
  绝对路径。
- **祖先目录**：从当前目录的父目录开始，沿目录树直到 doctidex 根目录的所有目录。
- **原子条目**：由其父目录的 `index.md` 标识、作为单一整体索引的子目录。
- **负责索引**：对某个目录范围承担索引责任的最近祖先 `index.md`。
- **源目录树**：通过挂载引入当前 doctidex 目录树的外部目录树。
- **挂载点**：源目录树在当前 doctidex 目录树中呈现的逻辑路径。
- **维护范围**：一次维护执行中被选定的单一目录树写入边界；维护所需的
  读取、编辑、结构检查和结果审阅均以该目录树的根目录为基准。
- **维护基准**：挂载类型或实现变体为维护工作识别的源目录树起始状态。
  基础协议不规定其表示形式，也不要求所有挂载类型必须定义它。
- **链接根目录**：解析以 `/` 开头的文档 link 时使用的目录基准。
- **保留目录**：由协议保留路径和语义、不得由普通内容赋予冲突含义的目录。

## 3. 目录结构

doctidex 目录树的最小结构如下：

```text
<doctidex-root>/
├── index.md
├── log.md                 # 可选
├── <其他文件>
└── <子目录>/
    └── ...
```

根目录必须包含 `index.md`。目录树可以包含任意层级的子目录和其他文件。
除第 3.1 节规定的保留目录外，本协议目前不限制其他文件的名称与格式。

子目录可以包含自己的 `index.md` 和 `log.md`；存在时，它们分别描述该子目录
范围内的索引和变更，并遵守第 5 节与第 6 节的连续性要求。

### 3.1 `/.doctidex` 保留目录

根目录下的 `/.doctidex` 是协议保留目录。路径中的 `/` 表示 doctidex 根目录，
不是文件系统根目录。协议或明确的协议扩展可以定义该目录内的名称与语义；普通
内容不得占用这些名称并赋予冲突含义。

当前协议定义 `/.doctidex/mounts` 为唯一的逻辑挂载命名空间。保留目录和挂载
命名空间不要求在没有相应内容时物理存在；实现可以按需使用目录、符号链接、文件
系统挂载或虚拟映射呈现它们。无论是否物理存在，根 `index.md` 的
`doctidex.excludes` 都必须包含 `path: .doctidex/mounts`。

## 4. Frontmatter

Frontmatter 使用文件开头由 `---` 分隔的 YAML 映射。

所有 `doctidex` 配置必须位于顶层 `doctidex` 字段下。协议不在其他顶层字段中
定义配置，以避免与其他规范冲突。顶层 `type` 是为兼容 OKF 保留的标识字段；
`doctidex` 内部处理始终以 `doctidex.type` 为准。

### 4.1 `index.md`

每个 `index.md` 必须包含：

```yaml
---
type: index
doctidex:
  type: index
---
```

doctidex 根目录的 `index.md` 还必须包含：

```yaml
doctidex:
  type: index
  root: true
```

`doctidex.root: true` 将当前目录标识为一个 doctidex 根目录。

`index.md` 可以包含以下可选配置：

- `doctidex.atomic_entries`：标识原子目录；
- `doctidex.excludes`：标识不属于当前 `doctidex` 的内容；
- `doctidex.protected`：标识当前目录树维护范围之外的内容。

`doctidex.mounts` 只允许出现在同时声明 `doctidex.root: true` 的根 `index.md`
中，用于声明逻辑挂载点。非根 `index.md` 不得包含 `doctidex.mounts`。
根 `index.md` 还必须在 `doctidex.excludes` 中包含
`path: .doctidex/mounts`。

目录过滤配置见第 5.2 节，挂载配置见第 9 节。

### 4.2 `log.md`

每个 `log.md` 必须包含：

```yaml
---
type: log
doctidex:
  type: log
---
```

## 5. `index.md`

### 5.1 强制要求

根目录的 `index.md` 是 doctidex 目录树的唯一必需文件，也是默认访问入口。

`index.md` 可以出现在任意子目录。若子目录包含 `index.md`，该目录的所有祖先
目录都必须包含 `index.md`。

`index.md` 必须是 UTF-8 Markdown 文档。除 `index.md` 自身和被排除的条目外，
它必须为所在目录直接包含的每个文件和子目录提供可识别的索引条目。

若子代目录不包含 `index.md`，距离该目录最近的祖先 `index.md` 必须递归索引
该目录内的全部文件和子目录。递归索引在遇到包含自身 `index.md` 的目录时停止，
由该目录的 `index.md` 继续承担详细索引责任。原子条目和被排除内容按第 5.2 节
处理。

### 5.2 目录过滤配置

`doctidex.atomic_entries`、`doctidex.excludes` 和 `doctidex.protected` 使用相同
的条件列表结构。每个条件必须使用以下形式之一：

- `path`：精确指定相对于负责索引所在目录的路径；
- `regex`：按完整相对路径进行正则表达式匹配。

```yaml
doctidex:
  type: index
  atomic_entries:
    - path: vendor
    - regex: '^generated(?:/|$)'
  excludes:
    - path: .git
    - regex: '(^|/)__pycache__$'
  protected:
    - path: external/source
```

同一配置中的多个条件取并集。条件可以匹配负责索引范围内任意深度的文件或目录，
不限制为直接子代。每个条件必须是仅包含 `path` 或 `regex` 其中之一的 YAML
映射，字段值必须是非空字符串。`path` 必须是不能超出当前 doctidex 根目录的相对
路径。正则表达式的具体方言暂未规定。

过滤配置采用最近负责制。条目只由负责其目录范围的最近 `index.md` 配置；条件
不跨越包含自身 `index.md` 的子目录边界，也不得在路径上的多个 `index.md` 中
重复声明同一条目。这一条件列表与最近负责制同样适用于后续目录过滤配置。

#### `atomic_entries`

`atomic_entries` 只标识目录。被匹配的目录视为原子条目，其整个目录树内不得包含
`index.md` 或 `log.md`。定义原子条目的负责索引必须索引该目录本身，并可以为
优化查询效果而选择性索引其内部内容，但不要求完整递归索引。

原子条目的边界只定义负责 `index.md` 如何组织该目录，不为内部文件建立新的
内容、读取或 link 边界。除不得出现 `index.md` 或 `log.md` 外，当前协议不对
原子条目内部内容施加递归符合性要求；其内部 Markdown link 的目标范围也不参与
当前 doctidex 目录树的 link 符合性判断。这不等于 `excludes`：原子条目仍是目录树
的可读条目，负责索引仍可选择性引用其内部内容，`protected` 也可与之同时生效。

#### `excludes`

`excludes` 可以标识文件或目录。被匹配的文件以及被匹配目录的整个目录树不被
当前 `doctidex` 识别，不承担索引、日志或其他符合性要求。

根 `index.md` 的 `excludes` 必须包含 `path: .doctidex/mounts`。此要求不依赖该
保留路径是否已经物理存在，并作为根级保留命名空间规则优先于普通过滤配置的
最近负责制。

#### `protected`

`protected` 可以标识文件或目录。被匹配的文件以及被匹配目录的整个目录树仍属于
当前 doctidex 目录树，但不得被以当前 `doctidex` 为范围的维护工作修改。协议只
定义该保护语义，不规定实现变体如何执行或验证保护。

该语义是没有更高优先级用户指示时的默认维护边界，不把内容变为不可修改对象。
用户可以显式授权对精确的 protected 内容执行维护，也可以授权调整或移除对应
保护配置。这种例外必须来自明确用户指示，不得由 agent 或实现工具自行推断或扩大。

`excludes` 与其他过滤配置同时匹配同一条目时，以排除语义为准。
`atomic_entries` 与 `protected` 可以同时作用于同一目录，两者语义同时生效。

### 5.3 推荐原则

`index.md` 应：

- 简要说明当前目录包含的知识；
- 使用 Markdown link 指向被索引的文件或子目录；
- 为人类和 agent 提供清晰的内容索引。

索引应提供足够的信息辅助 agent 渐进式读取。若子目录中存在 `index.md`，各级
索引应合理分层；在提供足够辅助信息的前提下，应精简内容并避免重复。

协议不要求固定章节或列表格式。

## 6. `log.md`

### 6.1 强制要求

`log.md` 是可选的 UTF-8 Markdown 文档，用于记录其所在目录范围内的重要变更。

`log.md` 可以出现在任意目录。若子目录包含 `log.md`，该目录的所有祖先目录
都必须包含 `log.md`。

若子代目录不包含 `log.md`，距离该目录最近的祖先 `log.md` 必须递归覆盖该目录
及其全部子代目录的变更。递归覆盖在遇到包含自身 `log.md` 的目录时停止，由该
目录的 `log.md` 继续承担详细记录责任。被排除的内容不属于该覆盖范围。

### 6.2 推荐原则

变更记录建议按日期分组、按时间倒序排列；日期建议使用 `YYYY-MM-DD` 格式。
协议暂不规定条目的固定结构。

## 7. 内容与扩展

Markdown 是文本知识的推荐格式，但不是其他内容的强制格式。Markdown 文档可以
使用 YAML frontmatter。除 `index.md` 和 `log.md` 外，协议目前不要求文档包含
frontmatter，也不规定概念类型；文档若包含 `doctidex` 配置，仍必须将其置于
顶层 `doctidex` 字段下。

doctidex 目录树可以包含自定义目录、文件和元数据。未知内容本身不影响整个目录树
的符合性，但不得占用 `/.doctidex` 中由协议或协议扩展保留的名称并赋予冲突含义。

## 8. 文档链接

`doctidex` 文档以 Markdown 文件路径 link 作为基础链接形式：

```markdown
[链接文本](文件路径)
```

协议不强制 link 只能使用标准 Markdown 语法。必要时，可以使用已经广泛应用、
可由目标 agent 或阅读器理解的 Markdown link 与 anchor 扩展形式。

相对路径以 link 所在文档的目录为基准。以 `/` 开头的路径以该文档的链接根目录
为基准，而不是以文件系统根目录为基准。普通 doctidex 文档的链接根目录是其
`doctidex` 根目录；挂载内容按第 9 节确定链接根目录。

### 8.1 路径边界

文档 link 的路径在形式上不得超出其链接根目录。检查路径时应按路径段处理 `.`
和 `..`；如果规范化过程需要越过链接根目录，该 link 无效。

边界检查不解析符号链接。符号链接在形式检查中视为目录树内的普通目录或文件。

### 8.2 路径形式

目录树内部链接应优先使用相对路径。相对路径中包含不超过 3 个 `..` 路径段时，
继续使用相对路径；超过 3 个时，应改用以 `/` 开头的根目录相对路径。

指向符合 doctidex 的外部源目录树时不适用上述相对路径推荐；此类路径引用必须
使用第 9 节规定的绝对内部路径。

```markdown
[相邻文档](../reference.md)
[较远文档](/topics/reference.md)
[外部目录树](/.doctidex/mounts/source/index.md)
```

### 8.3 推荐原则

引用文档时，应优先使用可导航的 Markdown link，而不应只写出路径形式的普通
字符串。link 与普通路径字符串可以同时使用。

标准 Markdown 形式足以表达目标时，应优先使用标准形式以保持可移植性。必要时，
可以使用 VS Code、GitHub 或成熟 Markdown 阅读器广泛支持且 agent 可理解的扩展
link 与 anchor 形式。

应灵活使用标准或扩展 anchor 将 link 指向文档中的具体内容，方便 agent 按需
读取。对于较长文档，尤其推荐使用 anchor 提供精确入口，避免为定位局部内容而
一次性加载整个文档。

```markdown
[具体章节](topics/example.md#具体章节)
```

扩展形式中的文件路径部分仍必须遵守本节的根目录基准和路径边界要求。用户对
link 或 anchor 形式有明确规定时，必须遵守用户要求。

### 8.4 尚未规定的引用语义

以下语义尚未规定：

- 链接目标的身份与完整性规则；
- 外部资料的引用、保存与溯源；
- 自定义引用类型及其解析方式。

在这些语义确定前，link 本身不声明特定关系类型。

## 9. `doctidex_mount` 逻辑挂载

`doctidex_mount` 是将完整的外部源目录树呈现在当前 doctidex 目录树中的声明式
逻辑挂载。`doctidex.mounts` 是根 `index.md` 中声明逻辑挂载点的列表。任意可由
挂载类型和实现变体定位的外部目录树都可以作为源目录树。

```yaml
doctidex:
  type: index
  root: true
  excludes:
    - path: .doctidex/mounts
  mounts:
    - type: git
      url: https://example.com/source.git
      mount_path: /.doctidex/mounts/source
```

每个挂载声明包含：

- `type`：必需，用于标识挂载类型；
- `url`：必需，用于标识源目录树，其具体语义由挂载类型和实现变体决定；
- `mount_path`：必需，表示源目录树在当前 doctidex 根目录下的绝对内部路径。

`doctidex.mounts` 必须是 YAML 列表，每个挂载声明必须是 YAML 映射。`type`、
`url` 和 `mount_path` 必须是非空字符串。每个声明始终挂载由 `url` 标识的完整源
目录树；基础协议不提供从源目录树中选择子树的配置。挂载类型可以定义其他扩展
字段，但不得改变完整源目录树挂载语义。

`doctidex.mounts` 只允许在根 `index.md` 中声明。每个 `mount_path` 必须是经过路径
段规范化的绝对内部路径，并且必须是 `/.doctidex/mounts` 的严格子目录，即至少在
该前缀后包含一个非空路径段。`mount_path` 不得使用 `.` 或 `..` 绕过此前缀，也
不得等于 `/.doctidex/mounts` 本身。同一根 `index.md` 中的 `mount_path` 不得重复，
也不得互为祖先与后代。

根 `index.md` 必须通过 `path: .doctidex/mounts` 排除 `/.doctidex/mounts`。因此
挂载点及其展开内容不属于当前目录树的索引、日志、符合性或维护范围，也不要求由
任何 `index.md` 索引。挂载内容的结构与语义仍归源目录树；源目录树本身符合
doctidex 时，其符合性独立于当前目录树判断。

当前目录树中所有指向符合 doctidex 的外部源目录树的路径引用，都必须使用以
`/.doctidex/mounts/` 为前缀的绝对内部路径，不得使用相对路径。该要求适用于文档
link、索引入口及其他以目录树路径导航到挂载内容的引用；挂载声明用于定位源的
`url` 不是目录树路径，不受此前缀要求约束。文档仍使用第 8 节规定的普通 link
语法，不引入专门的跨目录树 link 语法。

`/.doctidex/mounts` 在语义上不可嵌套。在一次从某个 doctidex 根目录开始的路径
解析中，只存在该根目录下唯一的 mount 命名空间。若已经位于该命名空间下又遇到
后续 `.doctidex/mounts` 路径段，后一个路径段重新表示本次解析起始根目录下的
`/.doctidex/mounts`，而不是前一个挂载点内的子目录。例如：

```text
/.doctidex/mounts/a/path/.doctidex/mounts/b
```

在语义上按以下路径处理：

```text
/.doctidex/mounts/b
```

存在多次嵌套时重复应用该规则，直到路径中只保留一个有效的 mount 命名空间前缀。
实现的物理目录或符号链接布局不得改变这一语义。

挂载源本身符合 doctidex 时，其中已有文档 link 的链接根目录和普通路径语义以源
目录树自身的 doctidex 根目录为准，而不是宿主目录树。以
`/.doctidex/mounts` 开头的路径是这一规则的例外，始终按上述不可嵌套规则回到本次
解析起始根目录的唯一 mount 命名空间。挂载源根 `index.md` 中的 mount 声明在源
目录树独立使用时仍然有效，但不会在宿主的 mount 命名空间内再创建嵌套命名空间；
宿主解析此类路径时，以宿主根 `index.md` 中的 mount 声明为准。

打包或分发目录树时，`mount_path` 对应节点及已展开的源目录树可以不包含在包内；
根 `index.md` 中的挂载声明仍描述其逻辑位置。源目录树的获取、恢复与物理挂载方式
由实现变体决定。实现可以使用挂载类型的原生机制，也可以集中管理源目录树并将其
映射到挂载点。

挂载点只是源目录树的读取入口。任何维护工作都不得以 `mount_path` 为写入
入口或透过挂载点修改源目录树；修改源内容时，必须从为该源目录树选定的
根目录进入。

维护范围按实际被修改的目录树划分，而不按到达它的 `mount_path`、挂载声明
或路径引用的数量划分。多个维护目标若被可靠确认为同一源目录树，并且在挂载类型
定义维护基准时具有相同基准，可以共用一个维护范围。当前目录树本身被可靠确认
为该源目录树时，当前根目录可以作为这个共用维护范围的写入入口。

彼此不同的目录树、不同维护基准，或者无法可靠确认目录树关系时，必须使用
独立的维护范围。同一项工作需要修改当前目录树与一个不同的挂载源时，必须
分别从两个目录树各自的根目录进入。

在一个维护范围的执行过程中，不得沿其内部的挂载点把其他源目录树直接纳入
当前写入边界。该目标必须重新作为维护目标判断应使用已有维护范围还是新的
独立范围。基础协议不规定目录树关系、维护基准或范围兼容性的具体判定方法。

没有对应根级 `doctidex.mounts` 声明的物理目录、符号链接或文件系统挂载不具有
`doctidex_mount` 语义。它不得被用来绕过符合 doctidex 的外部目录树必须位于
`/.doctidex/mounts/` 命名空间下的路径引用要求。

协议只规定挂载声明、逻辑位置和链接语义，不规定挂载的具体实现。

## 10. 功能扩展

查询、知识抽取及其他场景化行为不属于当前目录树结构规范。相关能力由实现变体
决定；
除非后续协议定义可观察的声明或结构，具体工具行为不构成协议要求。

## 11. 最小符合性

一个目录树符合当前协议雏形，需要满足：

1. 根目录具有非空目录名；
2. 根目录包含可读取的 UTF-8 Markdown 文件 `index.md`；
3. 根 `index.md` 包含 `type: index`、`doctidex.type: index` 和
   `doctidex.root: true`；
4. `/.doctidex` 仅按第 3.1 节作为协议保留目录使用，且根 `index.md` 的
   `doctidex.excludes` 包含 `path: .doctidex/mounts`；
5. 存在且未被排除的 `index.md` 和 `log.md` 使用第 4 节规定的类型标识；
6. `doctidex.atomic_entries`、`doctidex.excludes` 和 `doctidex.protected` 使用
   第 5.2 节规定的条件列表与最近负责制；
7. 原子条目内不包含 `index.md` 或 `log.md`，其内部其他内容不参与当前目录树的
   递归内容与 link 符合性判断；被排除内容不参与当前目录树的其他符合性判断；
8. 未被排除的 `index.md` 和 `log.md` 分别满足第 5 节与第 6 节的连续性要求；
9. 每个 `index.md` 按第 5 节索引其负责的目录内容，并按规定处理原子条目与
   被排除内容；
10. 每个 `log.md` 按第 6 节覆盖其负责且未被排除的目录变更；
11. `doctidex.mounts` 只出现在根 `index.md`，使用第 9 节规定的字段，并将完整源
    目录树挂载到 `/.doctidex/mounts` 的严格子目录；
12. 指向符合 doctidex 的外部目录树的路径引用使用第 9 节规定的绝对内部路径，
    mount 命名空间按不可嵌套规则解析；
13. 除原子条目内部和被排除内容外，文档 link 遵守第 8 节及第 9 节规定的
    路径形式、边界和挂载链接语义。

除上述要求外，其他内容不影响当前协议的符合性。本文档参考 OKF 基于目录、
Markdown 和少量格式约束的核心思想，但当前不声明严格的 OKF 格式兼容性。
