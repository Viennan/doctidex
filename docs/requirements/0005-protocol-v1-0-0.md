# 需求 0005：协议升级至 v1.0.0

link 根目录与路径范围决策。本需求没有修改 doctidex-git 的 Architecture、Skills、
CLI、Python 实现或测试。

## 1. 现状与问题核对

### 1.1 协议责任边界前后不一致

当前协议第 1.1 节已经声明：协议只规定目录树的可观察结构、内容语义和符合性，
不规定如何实现、构建或维护目录树。但后续规则扩大了这一边界：

- `doctidex.protected` 直接规定维护工作能否修改文件或目录；
- mount 规则规定写入入口、维护范围、维护基准、范围复用和跨 mount 写入边界；
- 最小符合性把这些维护相关规则纳入目录树是否符合协议的判断。

因此，`v1.0.0` 需要真正贯彻协议开头已经表达的边界，而不是继续在基础协议中协调
具体维护工作流。

### 1.2 mount 机制扩散到整个协议与实现

`/.doctidex/mounts` 当前不只是一个外部引用约定。它同时影响保留目录、根
`index.md` 的必需 `excludes`、mount 声明、绝对内部路径、链接根、不可嵌套解析、
打包、读取与维护范围，并占据最小符合性中的多项条件。

doctidex-git 为此提供 mount、resolve、maintenance scope/open 等命令，并在多个公开
Skill 中解释 mount 的准备、读取、维护和多根协作。用户实际使用时发现，这套机制使
协议和插件都难以瘦身，增加了 agent 的上下文负担和试错成本。

### 1.3 过滤标志与全覆盖索引增加理解成本

当前 `doctidex.atomic_entries`、`doctidex.excludes` 和 `doctidex.protected` 共用条件
列表与最近负责制，但各自又改变索引、符合性、读取或维护语义。实际应用表明，这些
区分的收益有限，难以抵消其理解成本。问题在这些字段及其派生语义，不在最近负责制；
后者符合渐进式披露原则，应在 `v1.0.0` 中保留。

当前协议还要求负责索引覆盖其范围内全部文件和目录。这会迫使 `index.md` 重复已有
overview、README 或下级索引已经承担的导航职责，增加维护成本，而不一定改善 agent
的实际发现路径。

### 1.4 Skill 数量不能替代清晰的心智模型

doctidex-git 当前具有 8 个公开 Skill。大量使用说明仍可能遗漏命令在工作流中的真实
作用。例如，`maintenance scope` 实际是可重复运行、无计划持久化的现场观察命令；
用户曾需要从实现反推这一心智模型，再反复修订 Skill 才使其用途清楚。

这一经验说明，`v1.0.0` 应优先降低协议本身施加给 agent 的概念数量和隐含前提，不能
依赖增加更多 Skill 文本来弥补基础模型的复杂度。

### 1.5 link 路径必须保有单一根边界

上一轮 Draft `v1.0.0` 允许结构化条目和 Markdown link 的词法路径越出 doctidex 根
目录，以便直接引用根外内容。这会使同一份文档的 link 同时受 doctidex 根和宿主目录
布局影响，削弱目录树作为可移植阅读边界的意义，也使边界判断混入宿主文件系统关系。

用户进一步明确：doctidex 根目录必须是其内部所有文件路径 link 的唯一链接根和形式
边界。外部内容的物理目标可以位于任意位置，但它必须先以 symlink、文件系统挂载或
其他方式获得一个根内呈现路径；协议 link 只引用该根内路径。

## 2. 用户意图与设计目标

### 2.1 核心原则

`v1.0.0` 应采用以下责任边界：

1. 对 `index.md`、`log.md` 及后续协议元信息的结构、字段和可观察语义给出明确规范。
2. 对目录树的读取、发现和导航只保留克制且必要的规范，优先使用推荐性规则。
3. 不规定实现如何创建、解析、校验、存储或同步目录树。
4. 不规定 agent 或其他实现如何规划、执行、隔离、授权或交付维护工作。
5. 规范中的每一项强制要求都应能用目录树及其文档的可观察状态判断，并且服务于读取
   或符合性，而不是服务于某个实现的工作流。
6. 元信息按最近负责制局部生效，使 agent 只在进入相关目录范围时承担理解该范围配置
   的成本。

简而言之，协议规定元信息如何影响读取，不规定实现机制，也不规定如何维护。

### 2.2 目标结果

升级后的协议应让人类和 agent 能够：

- 从 `index.md` 建立可靠的阅读入口，同时复用已有导航文档而不重复维护索引；
- 用普通 Markdown link 引用以 symlink、文件系统挂载或其他方式呈现在 doctidex 根内的
  外部内容，不必采用协议指定的物理存储布局；
- 将生成内容、外部源码、必须保持原样的内容作为整体说明或显式标记；
- 区分“可发现但不严格符合”的内容与严格符合的协议元信息；
- 用更少的专用概念理解目录树，降低插件 Skill 对解释协议复杂度的负担。

## 3. 协议变更设计

### 3.1 删除 mount 与旧过滤模型

`v1.0.0` 拟删除以下基础协议能力及其派生规则：

1. 删除 `/.doctidex/mounts` 逻辑挂载机制，不再强制外部目录树位于协议指定的目录
   结构，也不再由基础协议规定其声明、获取、展开、路径重写或不可嵌套语义。
2. 删除 `doctidex.mounts` 字段及根 `index.md` 必须排除 `.doctidex/mounts` 的要求。
3. 删除 mount 对文档 link、链接根目录、打包和最小符合性的特殊规则。外部内容如何
   到达、同步或映射由实现决定，但 doctidex link 始终以当前 doctidex 根目录为路径
   边界；根外内容必须先通过 symlink、文件系统挂载或其他实现方式呈现在根内，link
   不得直接使用越过根目录的路径形式。
4. 删除 `doctidex.atomic_entries`、`doctidex.protected` 和 `doctidex.excludes` 字段，
   以及这些字段的条件列表和相互优先级规则；保留独立于这些字段的最近负责制。
5. 删除协议中的维护范围、维护基准、写入入口、范围复用和维护授权规则。

### 3.2 保留元信息基础

除本需求明确改变的部分外，保留 `index.md` 与 `log.md` 的现有规范性和推荐性基础，
包括文件角色、Markdown/UTF-8 要求、frontmatter 类型标记、根标记、层级连续性和
面向人类与 agent 的渐进阅读目标。最终协议应逐项复核这些规则，避免因删除旧字段而
留下悬空术语或例外。

### 3.3 保留最近负责制

`v1.0.0` 保留并推广最近负责制，作为局部元信息的统一作用域原则：

- 每个 `index.md` 只配置其负责的目录范围；
- 子目录出现自己的 `index.md` 时，该文件成为子目录范围的最近负责索引，祖先
  `index.md` 的局部配置不跨越这一边界；
- 新增的 `boundary-set`、`atomic-indexing` 和 `unsafe` 应遵循这一原则；三者采用统一的
  结构化条目列表和相对路径类型，各字段只定义自身必要的条目属性，不能要求根索引
  汇总整棵目录树的局部配置；
- agent 沿索引逐步进入目录树时，在尚未读取某个子目录的 `index.md` 前，不需要加载、
  理解或推理该子目录内部才声明的配置。

最近负责制的价值是把认知成本限制在已经进入的阅读范围内，支持渐进式披露；它不是
旧过滤 flags 的附属行为，不应随这些字段一起删除。

`doctidex.boundary-set`、`doctidex.atomic-indexing` 和 `doctidex.unsafe` 是最终字段名。
三者均为带属性的结构化条目列表；`v1.0.0` 只定义相对路径条目类型。每个条目以声明它
的 `index.md` 所在目录为基准标识文件或目录，词法规范化后必须仍位于当前 doctidex
根目录内，并且能表示为从根目录出发、不包含 `..` 的相对路径。条目路径不得借
`boundary-set` 或物理 symlink 目标越过该路径边界。未来版本可以另行增加其他条目类型。

### 3.4 结构化 link 注释

结构化 link 注释是附着于单个 Markdown link 的 doctidex 元信息容器，使用形如
`<!-- doctidex: ... -->` 的 HTML 注释块表达。它向人类、agent 和程序暴露读取该 link
所需的客观辅助信息，不改变 Markdown link 自身的目标、解析规则或可访问性。

#### 3.4.1 与 link 的关联

一个 link 后可以紧跟多个 HTML 注释块，形成与该 link 关联的连续注释块序列：

- link 与第一个注释块之间、相邻注释块之间可以存在空白；
- 遇到首个既非空白也非注释块的内容时，该 link 的注释块序列结束；
- 序列可以包含其他标准的注释或文档原有注释；
- doctidex 注释可以位于序列中的任意位置，不要求是第一个注释块；为便于渐进读取，推荐
  把 doctidex 注释放在序列首位；
- 识别 doctidex 注释时不得移动、删除、合并或解释同一序列中的其他注释块，也不得因
  其他注释先出现而把后续 doctidex 注释视为与 link 无关。

下列 doctidex 注释仍与 link 关联：

```markdown
[External](/external/source.md)
<!-- another-standard: existing metadata -->
<!-- doctidex: ... -->
<!-- original document note -->
```

#### 3.4.2 字段

当前 link 场景决定结构化注释中哪些字段适用、必需或可选：

| 字段 | 要求与默认值 | 可观察语义 |
|---|---|---|
| `cross-boundary-point` | 非 `index.md` 跨界 link 必需；`index.md` 可缺省并由 `boundary-set` 推导 | link 路径从起点到首次跨越边界为止的前缀，包含边界目录自身。 |
| `unsafe` | 可选布尔值；缺省为 `false` | `true` 表示 link 指向的路径是 unsafe；`false` 或缺省表示该路径按当前 link 声明为 safe。 |

`cross-boundary-point` 必须标识同一 doctidex 根目录内的边界目录，采用第 3.5 节的
根绝对路径或根内相对路径形式，但不得包含 anchor。它不能借相对路径或 symlink 的
物理目标越出 doctidex 根目录。

`unsafe` 描述 link 指向路径的 doctidex 符合性，不描述 link 本身。`true` 不阻止读取、
索引或可达性计算。

#### 3.4.3 注释省略

只要当前场景存在必需字段，或者需要表达任一字段的非默认值，结构化注释自身就是必需
的。当所有适用字段均可缺省且均采用默认值时，整个 doctidex 注释也可以缺省；缺省
注释等同于其中所有适用字段分别取默认值。

关联序列中存在其他注释但不存在 doctidex 注释，同样视为 doctidex 注释缺省。其他
标准或原有注释的存在不改变 doctidex 字段的默认值，也不自动产生 doctidex 语义。

### 3.5 doctidex link 的根与路径形式

doctidex 中每个文件路径 link 的链接根目录都是该 link 所属 doctidex 的根目录。link
路径在形式上不得越出这个根目录。允许的文件路径形式只有：

1. **根绝对路径**：以 `/` 开头，`/` 表示 doctidex 根目录，不表示宿主文件系统根目录，
   例如 `/topics/reference.md#section`；
2. **根内相对路径**：以 link 所在文档目录为基准，按路径段词法规范化后仍位于
   doctidex 根目录内，例如 `../topics/reference.md#section`。

anchor 是可选的文档内定位部分，不参与路径边界计算。仅包含 anchor 的 link 等同于
指向当前文档的根内相对 link。相对路径的原始文本可以包含 `.` 或 `..`，但规范化结果
必须能改写为一个从 doctidex 根目录出发且不包含 `..` 的相对路径；如果规范化需要移动
到根目录的父目录，该 link 无效。路径判断只处理 link 的词法形式，不解析 symlink 的
物理目标。

因此，根外物理内容不能通过 `../../external/...` 等形式直接 link。实现可以用 symlink、
文件系统挂载或虚拟映射把外部目录树呈现在 doctidex 根目录的某个内部路径，再由 link
使用该内部路径。物理呈现方式不改变 link 根目录，也不把宿主文件系统路径提升为协议
路径。

### 3.6 `doctidex.boundary-set`

拟在 `index.md` 中增加 `doctidex.boundary-set`，用于标识 doctidex 根目录内部作为
内容边界入口的目录。边界条目自身必须是第 3.5 节规定的根内路径。一条 link 的根内
路径进入 `boundary-set` 中的目录时，就在当前根的阅读视角下发生跨界。该判断不解析
symlink 的物理目标，也不依赖目标是否已经存在；跨界是当前根路径视角下的语义，不是
对目标内容全局身份的判断。

其具体语义是：

- 目录树内任意文档可以使用普通 Markdown link 引用通过根内边界目录呈现的内容；
- 非 `index.md` 文档链接到边界目录内的内容时，其关联注释块序列必须包含结构化 doctidex
  注释，并通过 `cross-boundary-point` 指明首次跨越的边界；
- `index.md` 已通过 `doctidex.boundary-set` 提供边界信息，因此链接到 safe 路径时可以
  省略结构化注释；链接到 unsafe 路径时必须添加注释并声明 `unsafe: true`；
- 无法修改以补充强制注释的非 `index.md` 文档，必须由最近负责索引以 `unsafe` 范围
  显式标记；该范围应尽可能紧，但过宽不构成形式违反；
- 目录树内的 `index.md` 可以通过根内呈现路径索引外部内容，并可以复用该内容自己的
  索引，不要求在当前目录树中复制一套平行索引；
- 边界只影响读取与符合性判断，不规定外部内容的获取、权限、同步或维护方式。

`boundary-set` 的必要性之一，是在 link 路径不越出 doctidex 根目录、且协议不解析
symlink 物理目标的前提下，仍能显式暴露某个根内目录是外部或独立内容的阅读边界。

### 3.7 `doctidex.atomic-indexing`

拟增加 `doctidex.atomic-indexing`，用于把一个目录作为整体建立索引。被标记目录的
元信息放在目录之外，该目录内部不创建 `index.md`、`log.md` 等协议元信息；负责说明
它的外部 `index.md` 不必逐项覆盖内部文件，可以只说明该目录整体及其阅读入口。

这一能力用于生成、vendored、源码、资产或已经由内部权威文档充分导航的目录，目标是
减少侵入式索引，而不是隐藏内容或限制普通文件工具读取。

### 3.8 `doctidex.unsafe`

拟增加 `doctidex.unsafe`，用于显式标记不能或不应严格符合 doctidex 的文档或目录，
例如必须保持上游原样的文件、外部收集内容或刻意保留既有格式的目录。

协议只保留少量强制要求。已知内容违反这些要求但需要继续纳入阅读范围时，最近负责
索引必须用 `doctidex.unsafe` 显式声明例外；未声明的违反仍使严格符合性检查失败。

unsafe 内容可以同时位于 `boundary-set`，也可以仍位于当前目录树边界内。unsafe 范围
应尽可能紧，只覆盖无法满足强制要求的具体文档或最小目录范围。若更小范围足以表达
例外，强烈不建议把包含无关 safe 内容的共同祖先整体标为 unsafe，因为这会减少可严格
检查、可依赖和可渐进披露的内容，降低目录树可用性；但过宽声明本身不违反形式符合性。
被标记内容仍属于可读、可索引的目录树内容，只退出其明确无法满足的严格规则；
`unsafe` 不等同于删除后的 `excludes`，也不隐藏内容。

结构化 link 注释中的 `unsafe: true` 是同一符合性状态在阅读入口上的局部暴露：它提醒
agent 被链接路径不能按严格符合内容处理。字段缺省或显式为 `false` 时，该 link 把目标
路径声明为 safe；这里的 safe 只表示没有声明 doctidex 强制规则例外，不表示来源可信、
内容无害、允许修改或已经过安全审查。

`atomic-indexing` 目录内部没有负责索引时，其外部最近负责 `index.md` 可以直接把内部
某个文档或最小范围标记为 unsafe。该标记只向读者和工具暴露客观的符合性风险，不应
被解释为维护授权、禁止修改、来源可信或内容安全的判断。

### 3.9 从全覆盖改为可达索引

放宽 `index.md` 必须直接或递归枚举其负责范围内全部子代的要求。`index.md` 可以省略
已经由其他文档有效索引的文件或目录，但这些内容仍需从当前索引阅读链间接可达。

间接可达采用可计算的 Markdown 路径图：只跟随可读取、可解析 Markdown 文档中的文件
路径 link；普通文本提及、无法解析的 link、不可读取、不存在或在形式上越出 doctidex
根目录的 Markdown 目标不构成阅读链。通过根内 `boundary-set` 路径到达的 Markdown
索引只要满足边界注释或 unsafe 规则，也可以参与阅读链。验证应据此计算可达性，而不是
把完整性判断留作仅供人工复核的候选项。

例如，若已有 overview 文档提供了完整且高质量的子代导航，`index.md` 可以只链接该
overview；它也可以为了查询优化、突出关键入口或弥补原索引质量而继续直接索引其中
部分内容。协议不应强迫两份文档重复相同导航信息。

## 4. 用户场景与可观察结果

| 场景 | `v1.0.0` 的期望结果 |
|---|---|
| 复用仓库现有 overview | 根或父级 `index.md` 链接权威 overview，子代通过该阅读链可达，无需重复枚举。 |
| 引用外部知识库 | 实现把外部目录树呈现在 doctidex 根内并以 `boundary-set` 标记入口；文档只使用根内 Markdown link，注释可暴露边界和目标路径是否 unsafe。 |
| 索引源码或生成目录 | 外部 `index.md` 将目录作为整体说明，目录内部保持原有组织。 |
| 保留不完全符合的内容 | `unsafe` 明确暴露其符合性风险，但不把风险扩展解释成维护或信任策略。 |
| agent 渐进阅读 | agent 从 `index.md` 和间接阅读链发现内容，只在进入子目录范围时读取其最近负责索引和局部配置。 |
| 实现维护目录树 | 实现自行选择原生文件、Git、工作区或其他机制；协议不规定其维护流程。 |

## 5. 设计约束与非目标

1. 本需求只定义协议目标，不把 doctidex-git 当前命令、状态字段或 Skill 工作流提升为
   `v1.0.0` 的协议要求。
2. 不在基础协议中替代 mount 设计新的外部仓库获取、缓存、版本固定或同步机制。
3. 不把 `boundary-set`、`atomic-indexing` 或 `unsafe` 解释为访问控制、写保护、信任、
   所有权或安全扫描结果。
4. 不要求 `index.md` 重复高质量的现有索引，但也不禁止为了发现效率直接索引同一内容。
5. 不以减少文字篇幅为唯一目标；必须保留足以让不同 agent 得到一致读取判断的字段、
   默认行为、边界语义和失败含义。
6. 不在本需求中调整 doctidex-git。协议与实现的暂时差异必须明确保留给后续 Requirement，
   不能以当前插件行为反向限制 `v1.0.0` 的协议设计。
7. 不因删除旧过滤 flags 而废除最近负责制，也不把所有局部配置提升到根索引集中声明。
8. 不把允许实现使用 symlink、文件系统挂载或虚拟映射解释为允许 link 使用根外路径；
   物理目标位置与协议可见路径必须分开判断。

## 6. 兼容性与迁移影响

这是一项有意的不兼容重构：

- `v0.1.0` 目录树不能假定 `mounts`、`atomic_entries`、`protected` 或 `excludes` 在
  `v1.0.0` 中继续具有协议语义；
- 依赖 `/.doctidex/mounts` 路径重写、mount 声明或维护范围语义的实现需要后续重新设计；
- 索引覆盖要求将从文件树逐项覆盖转向阅读链可达，验证器的符合性判断模型会随之改变；
- 依赖相对路径直接越出 doctidex 根目录访问内容的文档不符合 `v1.0.0`；外部内容必须先
  以根内路径呈现；
- 新增的边界、atomic indexing 和 unsafe 标记需要定义清晰的数据结构、组合规则和
  错误处理；其作用域保留最近负责制，除此之外不照搬已删除过滤字段的隐含语义；
- doctidex-git 在后续对齐前继续实现 `v0.1.0` 模型，不应被描述为已经符合 `v1.0.0`。

不提供从 `v0.1.0` 到 `v1.0.0` 的迁移说明、迁移路径、兼容读取模式或迁移工具。
`v1.0.0` 按全新协议和全新实现处理；旧协议文件归档保存，不在原文件上改写成新版本。
新协议文件的发布状态继续使用 Draft，版本号与发布状态保持独立。

## 8. 验收标准

1. 当前 `v0.1.0` 协议文件原样归档，新的协议文件标记为版本 `v1.0.0` 和状态 Draft，
   当前协议导航指向新文件。
2. 新协议不提供从 `v0.1.0` 迁移的说明、路径、兼容读取模式或工具要求。
3. 协议不再定义 `/.doctidex/mounts`、`doctidex.mounts`、`atomic_entries`、
   `protected`、`excludes` 及其派生符合性规则。
4. 协议不再对维护范围、写入入口、维护基准、授权、同步或交付流程提出规范性要求。
5. `index.md`、`log.md` 及保留元信息的每个字段、默认值、作用域和错误语义均有定义。
6. `boundary-set`、`atomic-indexing` 和 `unsafe` 均定义为带属性的结构化条目列表；
   `v1.0.0` 只支持相对路径条目类型，所有条目规范化后都必须位于当前 doctidex 根内。
7. 最近负责制适用于局部元信息，祖先配置不跨越具有自身 `index.md` 的子目录边界，
   且根索引不需要预先汇总未进入目录的配置。
8. 每个 doctidex 文件路径 link 的链接根都是该 link 所属 doctidex 的根目录；允许形式
   只有以 `/` 表示 doctidex 根的根绝对路径，或以 link 所在文档为基准的根内相对路径，
   两种形式都可以附加可选 anchor。
9. link 的文件路径经词法规范化后必须能写成从 doctidex 根目录出发且不含 `..` 的相对
   路径；任何需要移动到根目录父级的 link 均无效。仅有 anchor 的 link 等同于指向当前
   文档，anchor 不参与路径边界判断。
10. 根外物理内容只有先通过 symlink、文件系统挂载或其他方式呈现在 doctidex 根内，
    才能成为有效 link 目标；协议判断不解析 symlink 物理目标，也不允许直接使用根外
    相对路径或宿主文件系统绝对路径。
11. `boundary-set` 只标识 doctidex 根内目录；跨界按当前根视角下的内部路径形式判断，
    不解析 symlink 物理目标，也不要求 link 目标已经存在。
12. 非 `index.md` 的跨界 link 后关联的注释块序列必须包含 doctidex 注释，其中
   `cross-boundary-point` 的值覆盖到边界目录自身；无法补充注释的最小内容范围标为
   unsafe。该范围应尽可能紧，但过宽不构成形式违反。`cross-boundary-point` 本身也
   必须标识同一 doctidex 根内路径。
13. 结构化注释支持可选布尔字段 `unsafe`；`true` 表示 link 目标路径为 unsafe，
    `false` 或缺省表示 safe。`index.md` 链接 unsafe 路径时也必须显式添加该注释。
14. link 后可以存在由多个 HTML 注释块组成的关联序列；doctidex 注释可以位于其中任意
    位置，其他标准或文档原有注释不阻断关联，但推荐将 doctidex 注释放在首位。
15. 当一个 link 场景的所有适用字段均可缺省并采用默认值时，结构化注释自身也可缺省；
    注释缺省等同于所有适用字段取默认值。有必需字段或非默认值时不得省略注释。
    关联序列只有其他注释而没有 doctidex 注释时，也按缺省处理。
16. safe/unsafe 只表示是否声明 doctidex 强制规则例外，不表示信任、安全、写权限或
    审查结论；两种状态的 link 都可以参与读取、索引和可达性计算。
17. unsafe 内容仍可读、可索引，只退出其明确违反的严格规则；范围应尽可能紧，过宽
    范围受到强烈不建议但不影响形式符合性，且 atomic-indexing 外部的最近负责索引
    可以标记其内部具体内容。
18. 索引规则允许复用已有导航文档，并只通过可解析且保持在当前 doctidex 根内的
    Markdown 文件路径 link 计算阅读链可达性；通过根内 `boundary-set` 路径到达且符合
    注释规则的索引可以参与该路径图。
19. 最小符合性与正文各章节一致，不引用已删除术语、字段或 mount 特例，并把 link 根与
    词法路径范围纳入强制检查。
20. 本需求不修改 doctidex-git 的 Architecture、Skills、代码或测试，并明确其后续对齐边界。

协议修订已实施。当前 Draft `v1.0.0` 权威正文见
[`spec/overview.md`](/spec/overview.md)，其中：

- [术语](/spec/overview.md#2-术语)区分链接根目录、根绝对路径和根内相对路径；
- [局部配置](/spec/overview.md#5-局部配置)要求三个结构化条目列表的路径词法规范化后
  保持在当前 doctidex 根内；
- [`boundary-set`](/spec/overview.md#51-doctidexboundary-set)只标识根内目录，并在
  不解析 symlink 物理目标的前提下计算边界穿越；
- [可达性](/spec/overview.md#7-可达性)只接受有效且根内的 Markdown 文件路径 link；
- [文档 link 与结构化注释](/spec/overview.md#8-文档-link-与结构化注释)定义根绝对、
  根内相对、anchor、路径栈下溢失败及根内 `cross-boundary-point`；
- [符合性](/spec/overview.md#11-符合性)把 link 根目录和路径范围纳入强制检查。

原 `v0.1.0` 正文仍不作改写地归档于
[`spec/archive/v0.1.0.md`](/spec/archive/v0.1.0.md)。仓库现有 link 和局部配置已经按
同一词法模型验证；doctidex-git 的设计、公开 surface、实现与测试继续留待后续
Requirement 对齐。
